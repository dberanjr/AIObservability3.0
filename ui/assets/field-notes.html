01

The gap traditional monitoring can't see

AI systems are probabilistic and data-coupled, so the same input can produce a different output, and a request can succeed technically while failing completely on quality. These four failure modes are invisible to latency-and-error monitoring. They are the reason AI observability exists as a category.

Silent hallucination

HTTP 200 · 48ms · 0 errors
Model returns a confident, well-formed answer that is factually wrong. Nothing in the infra signal flags it.
quality, not health

Quality drift

All requests still pass
Output degrades gradually as prompts, models, or user behavior shift. No single request fails; the aggregate gets worse.

Safety & injection regression

Conversational breakdown

02

The stack you actually instrument

"AI observability" is not one layer. A single thumbs-down in the UI has to be traceable down through the agent's decision graph, the model call, the retrieval step, and the GPU underneath. This six-layer model (Dynatrace's framing, and broadly the shared mental model) is the map. Most point tools cover the top four; full-stack platforms reach the bottom two.

Layer
Instrument what
Breaks how
L1

Application

signals
User interactions, feedback events (thumbs up/down), request metadata, session context.
failure
UI-triggered anomalies, feedback ratio drops, latency the user actually feels.
L2

Orchestration

signals
Prompt/response pairs, retries, tool-call timing, branching logic (LangChain, Semantic Kernel, custom).
failure
Runaway retries, wrong branch taken, tool timeouts, prompt-assembly errors.
L3

signals
Reasoning chains, goals, memory state, tool invocation history, intermediate outputs.
failure
Loops, bad tool selection, memory loss, trajectory that never reaches the goal.
L4

Model & LLM

signals
Raw prompts/completions, token usage, latency, cost, model version, guardrail scores.

Hallucination, timeouts, cost spikes, quality regression after a model swap.
L5

Retrieval & Vector DB

signals
Embedding quality, retrieval relevance scores, result-set size, query latency (Pinecone, Weaviate, FAISS).
failure
Wrong or stale context retrieved, tokenization drift, RAG feeding the model bad inputs.
L6

Infrastructure

signals
GPU utilization, memory pressure, network, inference cost, endpoint availability.
failure
GPU saturation, throttled endpoints, an infra timeout surfacing as an "AI error."

The dividing line between vendors is how far down the stack they can correlate. An eval tool that sees L1 to L4 tells you the answer was bad. A full-stack platform that also owns L5 to L6 tells you it was bad because a managed endpoint was throttling.

New pillars for a probabilistic system

Classic observability rests on metrics, logs, and traces. For AI, Braintrust's reframe is the useful one: the pillars shift to traces, evals, and annotation. For enterprises there is a fourth pillar you cannot skip, cost and operational correlation, because AI spend and AI incidents both land on someone's budget and someone's pager.

+ Fourth pillar · non-negotiable at enterprise scale

Cost & operational correlation. Token and model spend attributed per request, user, and version, plus the tie-back from a quality failure to the infra, app, or business impact it caused. This is what turns AI observability from a developer tool into something a CIO and a CFO will fund.

05

What they share vs where they split

Every serious tool clears the same low bar. The market separates entirely on the right-hand column, and that column is where price, lock-in, and real value live.

Table stakes · everyone has this

  • Trace & span capture of prompt, response, and the steps between
  • Token & cost tracking across providers and models
  • Latency metrics per call and per pipeline
  • Aggregated dashboards for trends over time
  • OpenTelemetry ingest (increasingly the default integration path)
  • Framework hooks for OpenAI, LangChain, and the common SDKs

Differentiators · where tools diverge

  • Built-in eval depth: research-backed LLM-as-judge metric libraries vs "bring your own"
  • Quality-aware alerting: fire on eval score drop, not just latency
  • Drift detection at prompt, model-version, and user-segment level
  • Annotation workflows usable by non-engineers (PM, SME, QA)
  • Production-to-eval loop: traces auto-curated into regression datasets
  • Prompt management with versioning and runtime updates
  • Agent simulation and pre-production scenario testing
  • Full-stack + security correlation and causal root cause
  • CI/CD gating that blocks a release when quality regresses
  • Self-host / data residency and the pricing model itself

06a · solutioningComposing the eval-first archetype on Dynatrace

Not a parity claim. A capability-by-capability map from the eval-first feature set to the Dynatrace primitives that deliver it: Workflows (scheduled or event-triggered automation with a JS runtime, outbound fetch, and credential vault), OpenPipeline (ingest and enrichment of logs, metrics, and business events with arbitrary attributes into Grail), Site Reliability Guardian (DQL-scored release objectives wired into CI/CD), AppEngine (custom apps over Grail), and native hyperscaler AI-service ingest. Status legend: native ships today, compose wires shipped primitives together, build means an AppEngine app carries the workflow, gap means a genuine gap, stated plainly.

06b · hardeningThe developer-tracing claim, made precise

"Dynatrace covers the developer/OSS archetype" survives scrutiny only if each appeal of that archetype maps to a concrete capability. Point by point:

Functional parity, point by point

  • OTel-native: first-class OTLP ingest including the GenAI semantic conventions; instrument once with the same SDKs Langfuse or Phoenix use, point the exporter at Dynatrace
  • Zero-config capture: OneAgent auto-instruments alongside OTel, so coverage extends to services nobody hand-wired
  • SQL-grade queryability: DQL over raw spans in Grail matches the "query my traces like data" appeal (PostHog's SQL pitch, Langfuse's ClickHouse) with joins to logs, metrics, and bizevents the point tools can't make
  • No per-seat tax: consumption pricing means the whole team gets in; the per-seat friction of LangSmith-style pricing doesn't apply
  • Fast dev loop: free trial tenants, local OTLP export, and the Distributed Tracing and Notebooks apps give the inspect-iterate loop developers actually use
  • Framework coverage: LangChain, LlamaIndex, OpenAI, Anthropic, Bedrock flows arrive via the same OTel path; no proprietary SDK required
  • Granular cost governance: ingest and license cost is attributable to user, team, or application over any timeframe; cost reports are automatable and trendable for scheduled delivery to those owners
  • Cost anomaly alerting: automatic, customizable cost-anomaly notifications ship in-product, and DQL can detect a spend anomaly in a Workflow and route it to the right owner (the same runtime could disable a config or access, though that is rarely advisable)
  • Long retention, cheaply: raw spans are free for 10 days, and Grail bucketing retains spans, logs, metrics, sessions, and events for up to 10 years at a cost structure the point tools cannot match

Residuals, stated without spin

  • Not open-source, not self-hostable. For teams whose requirement is auditable code or data-plane ownership on their own metal, this is disqualifying regardless of features
  • No free-forever tier. The hobbyist and seed-stage on-ramp belongs to Langfuse and Phoenix; Dynatrace enters at team scale
  • Query is a metered cost, not a free-for-all. Grail bills by scan volume, so cost discipline shifts from "what you keep" to "what you scan." Guardrails cap runaway queries, but teams used to unlimited local querying adjust the habit
  • High-fan-out agents still need attention. Agent span volume is real; the difference is that the governance and anomaly tooling above make it a managed number, not a surprise

Why "consumption pricing" is a strength here, not a caveat

The instinct to file consumption pricing under risk comes from tools where ingest, indexing, and query are one escalating meter. Grail splits them, and the split is the point: keep data cheaply, pay for the fraction you actually read.

cheap
Ingest

Cheap by design, and much AI span telemetry is emitted from the cloud provider, so it lands as pure ingest. No premium for the AI layer.

→
cheap
Retain

No indexing, no schema to maintain, parse-at-query. 10 days free on spans, up to 10 years via bucketing. Retention stops being the thing you ration.

→
metered
Query

Metered per GiB scanned, with guardrails against runaway cost. Most users scan the slice tied to their question, not the whole lakehouse, so real query cost tracks use, not volume held.

net effect

A massively-parallel DQL engine over a no-index lakehouse lowers TCO on both the data and query layers, and every cost above is itself queryable, attributable, and alertable.

The two numbers the sticker price hides

OSS is not free. Langfuse and Phoenix carry a $0 license and the highest labor. Self-hosted Langfuse lands near $195k in year one, almost entirely build, maintenance, and infra, because you deploy the platform, build the eval and alerting layer it does not ship, and run it. The line item you see is $0; the one you pay is a half-FTE.

Eval-first tools price only the AI slice. Braintrust, Confident AI, Arize, and the rest cover evaluation, not infrastructure, security, or business correlation. To reach full-stack coverage, add an APM underneath. With a moderately-priced APM that lands the eval-first camp at $180–230k; if that APM is Datadog specifically, it is far more, because Datadog's per-SKU meters and overage bills push a matched full-stack deployment toward ~$360k. Either way it sits above Dynatrace's one-plane ~$150k (nearer ~$100k incremental for an existing customer), because Dynatrace is one consumption meter rather than an eval tool plus a stacked-SKU APM plus in-house glue.

The honest read. No tool here is cheap at production scale; the category floor is real. New Relic looks like the low-cost full-stack option because its ingest is genuinely cheap, but it is priced per full-platform user seat at roughly $400/user/month, so its real cost scales with how many people need full access: ~$90k for the core team here, and toward ~$240k on a broad enterprise rollout as seats multiply, and it still has no eval capability. That is its own version of the surprise: Datadog escalates per SKU, New Relic escalates per seat. Dynatrace has neither, no per-SKU stacking and no per-user or per-seat fee, so adding people or capabilities does not change the meter. Toggle the coverage control above and Dynatrace is the only full-stack option that holds flat. It is also the lowest eval-capable full-coverage option once you count what each number actually buys, one plane against the eval-first camp's two tools plus an APM plus glue. The real decision is not "which line item is smallest" but "which set of capabilities am I buying, and how does the bill move as the team and the data grow."

06d · the pricing mechanicThe floor is not the price

The reason full-stack Datadog and Dynatrace land so far apart is not the sticker rate, it is the model. Datadog advertises a low per-host entry that covers only the base infrastructure agent; every additional signal type is a separate SKU with its own commit, its own overage premium, and High Watermark billing that lets one brief spike define the whole month. Dynatrace turns every signal on through one agent under one consumption commit, and charges the same rate whether you are inside your commit or over it. The opinionated take

The two expensive mistakes are symmetrical. Buying an AI-native eval silo that cannot see infra, cost, or business impact leaves SRE, security, and finance blind. Relying on APM that only watches latency leaves the AI team blind to whether the answer was any good.

The winning pattern is a correlation plane plus eval depth: either one platform that credibly does both, or a deliberate two-tool split (full-stack for operational, cost, and correlation; AI-native for eval, prompt, and annotation) wired together over OpenTelemetry as the shared bus. Pick the split on purpose. Do not arrive at it by accident and call it a strategy.

Where Dynatrace sits, without the spin

An honest read, not a pitch. Dynatrace is firmly in the full-stack enterprise archetype: strong exactly where the eval-first tools are thin, and trailing exactly where they lead. Both columns below are stated plainly, because a decision this size should be made on the real trade-offs.

Genuine strengths

  • Six-layer instrumentation with correlation all the way down to GPU and managed endpoints
  • Dynatrace Intelligence causal root cause across metrics, logs, and traces on one topology, pivoting a bad prompt to the user action, session, and non-AI spans that produced it
  • Exact per-prompt token and model cost from editable per-model rates, tied to real request and business context, never a blended estimate
  • Runtime security: guardrail signals, PII exposure, injection surface, in the same plane
  • Auto-instrumentation and OpenTelemetry ingest, so coverage scales without hand-wiring
  • One governance, licensing, and access plane an enterprise can actually administer

Honest residuals vs AI-natives

  • No shipped eval-metric library (DeepEval carries 50+ research-backed scorers); rubrics are yours to define in the judge workflow
  • Prompt registry and runtime prompt push are absent; versioning is git plus span attributes, which answers attribution but not ergonomics
  • Annotation queues are buildable on AppEngine but are not a shipped feature; eval-first vendors sell them as product
  • Dataset curation and reconciliation are DQL patterns, not entities; no experiment-comparison screens
  • Agent simulation and adversarial scenario generation are a genuine gap, not a composition target

How to deploy this in practice

Start from the coverage math in section 07: one platform natively owns full-stack, functionally covers developer tracing, and composes ~90% of eval-first from Workflows, OpenPipeline, SRG, and AppEngine, with the judge scores, gates, and business joins living on the same Grail plane as everything else. The residual is specific and namable: a prompt registry UI, an annotation product, experiment-comparison screens, and agent simulation. That leaves two clean paths, and both work. A platform team builds the residual once on AppEngine and keeps a single governance plane, or a dedicated eval tool plugs in over OpenTelemetry with its results landing in Grail if you already own one. Either way, the correlation, cost, and security plane, the part no eval-first tool can replicate, stays on one platform. Section 12 shows this built and running on live telemetry from a real Dynatrace customer.

On competitive framing: some eval-first vendors assert Dynatrace has "no output-quality eval." That overstates it. Dynatrace does capture guardrail and quality signals, including hallucination, grounding, relevance, and PII. What is fair to say is that the eval-metric depth and workflow ergonomics of dedicated eval platforms are ahead today. That trade-off is real and worth weighing against the full-stack correlation, cost attribution, and scale that only a platform of this kind provides.

11b · the detectorsEleven problem patterns, two detector classes

The patterns are the one-click filters behind the Prompts and Agents tabs. They split by where the signal lives. A same-span predicate fires on the LLM or prompt span itself: a DQL filter is ANDed onto the prompt list. A cross-span trace scope signals on a different span in the trace, so a resolver finds the trace ids first, then scopes the prompt list to them. Thresholds are tenant-calibrated, and every wide query pre-filters before the group-by to stay under Grail's ~10-second wide-scan ceiling at roughly 6.7B spans/day.
